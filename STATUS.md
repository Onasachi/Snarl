# Where snarl is

Read this first. `PLAN.md` is the long history and the reasoning; `contracts/DEPLOY.md` is
the runbook. This file is the short answer to "what is true today and what is next".

Last updated: 2026-11-04.

## What snarl is

A mobile web puzzle game. Untangle a knot, free a creature, grow a pond.

**It is gated: nobody plays without connecting.** The splash is the door, with two ways
through — "Connect wallet" for whatever EVM wallet the browser has, and "Log in with
email" for Web3Auth. This reverses an earlier decision that play should be free with or
without a wallet, and it is worth knowing it was a decision rather than an accident: the
cost is first-time players who bounce at the door, which is the usual cost of a gate.

What is still *not* required is GoodDollar verification. A wallet is enough to play; the
face check is only for claiming UBI, entering the weekly pool, taking a name, or putting
a creature on the board.

## Next, in order

1. **Open a week.** Nothing about the weekly pool works until one is open — not entering,
   not the pot, not the screen's pool row. `2026-W45` is already the week players are in
   and is not open. `2026-W46` must be open before **Sunday 2026-11-08 10:00 UTC**, which
   is when it becomes Monday at UTC+14.
   Either the admin screen (`?weeks`, connected as the owner) or:
   ```
   cd contracts && WEEKLY=0x4B901584C3AdD752a1bc25415D2a1997A7701612 WEEK=2026-W45 PRIVATE_KEY=… pnpm hardhat run scripts/open-week.ts --network celo
   ```
   Open with no pool. Players fill it; a week with no money still awards Glint.
2. **Verify the sources on Celoscan.** Needs an Etherscan API key (one key, all chains,
   V2). Changes nothing about what is deployed — `check-live.ts` already proves the code
   is this code — but it is what makes the source readable to anyone else.
3. **Move both owners to a multisig.** Both are `Ownable2Step`: `transferOwnership(safe)`,
   then the Safe calls `acceptOwnership()`. Nothing moves until it accepts.
4. **A dashboard of real activity.** GoodBuilders asked another project for one and it is
   the remaining weak point here. Everything needed is on chain already: `playerCount` and
   each record on the board, `Gifted`/`Opened` events, weekly entrants and streaks.

## Things that will bite you

- **A week number can be opened once, ever.** The timestamps come from
  `contracts/test/fixtures/weeks.json`, generated by `scripts/weeks.mjs` and checked
  against the game's own `weekKey`/`weekId`. Never type one by hand.
- **A creature's number on the board is permanent.** `contracts/test/fixtures/roster.json`
  pins them and a test enforces it. Adding a creature means the next free number; never
  renumber.
- **GoodDollar runs three identity contracts on Celo mainnet** — production, staging and
  development. A person verified on one is a stranger to the others. `VITE_GOODDOLLAR_ENV`
  decides which, and anything unrecognised falls back to production.
- **Verification expires on a ladder starting at three days.** `reverifyDaysOptions` is
  `[3, 180]` and `authCount` cycles, so this hits everyone, not just newcomers. `collect`
  deliberately does not re-check verification for this reason. Lapsed is shown as "needs
  another look", not "not verified".
- **Gas is the expensive part of anything small.** Celo's floor is ~200 gwei, so a G$
  micropayment costs more in fees than it moves. That is why backing a week starts at
  500 G$ and why `prove` ranges 0.013–0.141 CELO depending on the creature.
- **There is no testnet.** Alfajores is retired; Celo Sepolia has no GoodDollar. The
  rehearsal is a fork of Celo itself: `cd contracts && pnpm test:fork`.

## Running it

```
pnpm dev                 # the game
pnpm test                # 240 app tests
pnpm build
cd contracts && pnpm test        # 80 contract tests
cd contracts && pnpm test:fork   # 18 more, against real Celo state
```

Useful URLs in development:

- `?wallet=demo` — a wallet that holds nothing and moves nothing, for driving every state.
- `?weeks` — the admin screen. The contract's `onlyOwner` is the only real guard; this
  flag just stops showing players buttons that would revert.
- `#gift=…` — opening a gift link.

## Social login

Wired, off by default. `VITE_WEB3AUTH_CLIENT_ID` turns it on and it appears in the wallet
sheet beside the detected wallets. Unset, none of it ships — the bundler proves the code
unreachable and drops the SDK. Set, it is about **900 KB gzipped** against 173 KB for the
whole game, loaded only when somebody chooses it.

Setting it up:

1. Make a project at `dashboard.web3auth.io`. Pick **Sapphire Mainnet** unless you are
   testing, and set `VITE_WEB3AUTH_NETWORK=sapphire_devnet` if you pick Devnet — a client
   id from one network does not work against the other, and that is the usual cause of a
   login window that opens and then fails.
2. **Whitelist every origin the app is served from**, `http://localhost:5273` included.
   Web3Auth refuses origins it has not been told about.
3. Put the id in `.env` as `VITE_WEB3AUTH_CLIENT_ID`.

Celo is pinned in `src/wallet/social.ts`, not left to the dashboard: the SDK uses only the
chains it is given, so the wallet is on Celo whatever the dashboard says. The window draws
in the game's own theme rather than arriving white over a dark pond.

**`web3auth.provider` is a setter with no getter in v11.** Reading it gives `undefined`
forever, which looks exactly like a login that worked and then produced nothing. The
provider is on the `Connection` that `connect()` returns, as `ethereumProvider`.

**Do not try to trim the Web3Auth window from code.** `modalConfig` is a trap: naming
some connectors makes the SDK dereference the ones left out, and `hideWalletDiscovery`
on its own makes it dereference a connector map that is not there. Both throw *inside an
event handler* during `init`, so nothing looks wrong — the window opens, the login
succeeds, and then there is no provider at the end of it. A green tick, and then straight
back to the door. Which login methods and wallets the window offers is a setting in
Web3Auth's dashboard; set it there.

**On localhost the console says `[hCaptcha] Warning: localhost detected`.** The window
still opens, but a sign-in may not complete there — test that part on a real host. Note
too that Web3Auth's own window offers MetaMask and several hundred other wallets, so with
this switched on it is a way in for people who do have a wallet as well.

Signing in this way does not make somebody a verified person: GoodDollar's face check is
tied to an address, and an address made by logging in with Google starts unverified like
any other. It can go through that check — it is just an address.

## Diagnosing "it does not see my wallet"

```
cd contracts && ADDRESS=0x… pnpm hardhat run scripts/check-identity.ts --network celo
```

Tells apart: verified, verified through a linked wallet, lapsed, verified against a
different registry, and never verified.
